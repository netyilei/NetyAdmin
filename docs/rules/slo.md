# SLO 与性能预算

> 数值权威源 = 本文件（为设计快照，数值变更只改本文件）。模块级 SLO 在各模块 Manifest 的 `slo` 字段声明，本文件定义全局预算、测量口径与压测纪律。
> 对 「基准测试入 CI」的落地取舍：微基准走手动触发 workflow（避免 CI 噪声），k6 压测本机直连执行（不用 docker）——见 §5。

## 1. 全局性能预算

| 调用 | 预算（p99） | 备注 |
|------|------|------|
| 本地 Port 调用 | < 1ms | 同进程，无网络 |
| 内部 RPC（同机房） | < 10ms | HTTP/JSON |
| DB 简单索引查询 | < 20ms | 慢查询另立优化项，不含全表扫描 |
| 读 API | < 200ms | 含鉴权/限流/序列化 |
| 写 API | < 500ms | 含事务 |
| WS 消息投递（同节点） | < 50ms | 起 |

配套规范（不重复展开）：跨模块读取优先批量端口、缓存热点、禁止循环内 RPC、远程调用必须超时/熔断/重试（仅幂等）、审计异步、WS 有界队列——见。

## 2. 可用性目标

- 基座默认可用性 **99.9%**（模块 Manifest `slo.availability` 以 **0–1 小数**声明，默认 `0.999`，可声明更严值）。
- 就绪口径：`/health/ready` 依赖检查通过；滚动发布期间单实例不可用不计入违约（N-1 窗口）。

## 3. 测量口径

- 延迟一律 **p99**（服务端视角，含中间件全链路），窗口 1 分钟滚动；压测报告同时给出 p50/p95/p99/max。
- 指标命名遵循 docs/rules/namespaces.md（Prometheus 指标命名空间）；request_id/trace_id 贯穿便于分位归因。
- SLO 达标判定以**基准压测 + 线上指标**两者为准；压测不过线 = 不达 SLO，禁止"线上再观察"搪塞。

## 4. 压测纪律（防假数）

1. 本机直连 PG/Redis（不用 docker）；压测前记录机器规格（CPU/内存/Go 版）。
2. 服务以 release 构建运行（`go build`，非 `go run`），debug 关闭，日志级别 info。
3. 预热 ≥10s 后才开始计量；每场景 **≥3 轮**，取中位数；单轮最好的数字不作为结论。
4. 目标按**峰值**设计（AGENTS §3），压测负载 ≥ 预估峰值 1.5 倍。
5. 阈值断言写在 k6 `thresholds` 里（读 200ms/写 500ms），脚本红即不达标；禁止跑完人眼看曲线。

## 5. 基准工具（scripts/bench/）

| 入口 | 用途 | 启用时机 |
|------|------|---------|
| `node scripts/bench/run.mjs` | 聚合入口：Go 基准 + k6 场景 | 起（目标随里程碑接入） |
| `go test -bench` | kernel/模块级微基准（Port/序列化/缓存） | 起有真实实现 |
| `k6/health-smoke.js` | 服务存活 + 读基线（p99<200ms） | 服务可跑后 |
| `k6/api-read.js` / `k6/api-write.js` | 读/写 API 场景模板（阈值已按 §1 写死） | 垂直切片后填真实端点 |

- 目标不存在的场景显式 SKIP（与 scripts/ci 同纪律）；k6 本机安装（Windows：`winget install k6 --source winget`），不进 CI 常规门禁，基准 workflow 手动触发。
