# 反过度设计规则（V2）

> 加严全局 `G1-07`。目标：专业但不臃肿；基础必须有，猜测性功能一律不做。
> 面向 AI/开发者：默认 MUST；违反需 ADR + 用户确认。

## 1. 定义

**过度设计** = 为"可能的需求"增加抽象、配置、模块、依赖或流程，当前没有真实使用者或证据。

**不算过度设计（必须做）**：模块边界、数据所有权、幂等、超时、降级、安全、审计、可观测、版本化、迁移、测试、契约。

## 2. 五道闸门

1. **证据闸**：谁在用、何时用、不用会怎样；无具名使用者/场景 → 不做。
2. **最简闸**：标准库 > 现有依赖 > 新依赖 > 自研；单实现不抽接口（真实边界除外）。
3. **复杂度预算**：新模块/子系统/依赖/配置/抽象计入预算；超预算需 ADR。
4. **可逆闸**：优先可逆方案；不可逆（API/DB/事件）必须版本化 + expand-contract + 回滚。
5. **删除闸**：N 个版本无使用或指标低于阈值 → 删除；dead code/flag/dep 立即清。

## 3. 复杂度预算（初始值）

| 项 | 预算 | 超限处理 |
|----|------|---------|
| Kernel 直接依赖 | ≤ 25 | 新增需 ADR + 清单登记（许可/维护/安全/体积）；CI `check-deps-budget` 硬门禁 |
| 模块数量 | 初始 ≤ 12 | 新模块需 2 个真实用例 |
| 单模块配置项 | ≤ 10 | 超限需说明运维必要性 |
| 抽象/接口 | 单实现不抽 | 仅 remote/external/test 边界用 Port |
| 代码生成 | 手工重复 ≥ 3 次才做 | 先模板/脚手架 |
| 新子系统 | 2 个消费者或测量瓶颈 | 否则用现有子系统 |
| 性能优化 | 有 Profile/压测证据 | 未测量不加缓存/索引/分片/队列 |
| API 字段/端点 | 有明确调用方 | 不做投机字段 |

## 4. 禁止清单（V2.0）

- 微服务 / Service Mesh / 多地域双活。
- Event Sourcing / CQRS / GraphQL。
- 动态插件 / WASM 运行时加载（插件市场规划内后置、仅预留架构，V2.0 不做市场功能）。
- 内置搜索 / 数仓 / OLAP / ML。
- 多租户全表改造、分库分表中间件。
- 自研 ORM / HTTP / 日志 / 配置框架。
- 为单实现抽 interface（Port 边界除外）。
- 每个行为一个配置项。
- 保留 deprecated 路径超过一个 major。
- 未测量就加缓存/索引/分片/队列。

## 5. 必须做（不是过度设计）

- 模块边界 / Port / 数据所有权 / 迁移。
- 幂等 / 超时 / 重试 / 熔断 / 降级。
- 安全基线 / 审计 / PII。
- 可观测：日志 / 指标 / trace / request_id。
- 版本 / 弃用 / 兼容。
- 测试 / 契约 / CI。
- 新模块 SLO 与容量评估。

## 6. 评审问题（设计/PR）

1. 谁在用？何时用？不用会怎样？
2. 最简方案是什么？为什么不够？
3. 新增了什么抽象/配置/依赖/模块？能否删除？
4. 是否可逆？回滚方案？
5. 证据是什么（用户需求/压测/Profile/错误日志）？
6. 触发条件与 kill criteria 是什么？
7. 是否重复已有能力？
8. 文档/规则/契约是否同步？

## 7. 触发式建设

- 功能默认"未建"；达到触发条件才建。
- 触发条件写入 ADR/issue；未触发不得提前实现。
- 触发后仍按五道闸门评审。
- 触发条件示例见。
